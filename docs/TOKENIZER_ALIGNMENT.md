# 分词器与模型 ID 空间错位 —— 故障复盘

> 本文记录一个**静默正确性缺陷**的完整复盘：系统不报错、不崩溃、有正常输出，但语义计算结果不携带语义信息。
>
> **状态**：**已修复并验证**。分词表已用 `tools/rebuild_sentencepiece_model.py` 重建（方案二），
> 切词行为与修复前逐字一致，语义区分度由 **−0.0149** 转正至 **+0.2894**。C++ 代码无需改动。

---

## 1. 摘要

本项目用 SentencePiece 把评论文本切成 token id，再交给 ONNX 模型编码成 384 维句向量，最后用余弦相似度做语义筛选。

**词表 id 与模型 embedding 行号整体错位 1 位**，导致每个 token 取到的都是**词表中相邻的另一个词**的向量。程序全程无任何异常。

| | 相关句对平均余弦 | 无关句对平均余弦 | 区分度 |
|---|---|---|---|
| 修复前（错位） | 0.6860 | 0.7010 | **−0.0149** |
| 修复后（对齐） | 0.8852 | 0.5957 | **+0.2894** |

即：**修复前语义区分度接近零、方向还略微相反**——程序一直在输出数值，但那些数值几乎不含语义信息。修复后区分度达到 +0.29。

> 口径说明：上表使用**项目实际链接的 sentencepiece.lib 真实分词结果**。
> 早期排查中曾用"贪婪最长匹配"近似分词，得到 −0.1337 / +0.2569；真实分词下症状没有近似版那么夸张，
> 定性从"系统性反转"修正为"区分度失效"。结论方向不变，但数值以本表为准。

---

## 2. 现象

### 2.1 表面现象

完全没有异常：

- 分词器 `Load()` 返回 `ok()`
- 每次分词都返回合法的 token id
- 所有 id 都在模型词表的行数范围内，不越界
- ONNX 推理正常返回 `[batch, 128, 384]` 的浮点结果
- 程序运行、界面交互一切正常

### 2.2 真实症状

语义区分度失效：相关句对与无关句对的平均余弦几乎相等（0.6860 vs 0.7010），方向还略微相反。

与"精度不够"的区别在于：**不是偶尔判错，而是输出的数值本身不携带语义信息**——看起来有结果、有小数、有排序，但排序与语义无关。

---

## 3. 排查过程

### 3.1 被证伪的两个假设

排查中有两个错误假设，记录下来，因为它们本身就是教训：

| 假设 | 依据 | 被推翻的方式 |
|---|---|---|
| "模型不是 MiniLM" | `model.onnx` 有 448MB，与英文 MiniLM-L6（约 90MB）相差过大 | 直接解析 initializer：总参数 117.5M、隐藏维 384、12 层 → 是**多语言** MiniLM-L12-H384。448MB 来自 250k 词表的嵌入矩阵，不是层数多 |
| "分词器与模型是配套的" | 特殊词元是 `<s>`/`</s>`，与 XLM-R 体系命名一致 | 命名风格一致 ≠ id 编号一致。逐 id 比对后推翻 |

**共同错误模式**：用"表面相似性"（文件大小、命名风格）替代"真正相关的测量"（维度、词表、行号）。

### 3.2 有效路径

三个动作定位了问题：

1. **解析模型**：读 ONNX 初始张量，得到 `word_embeddings = (250037, 384)`、12 层、117.5M 参数
2. **解析分词表**：读 SentencePiece 的 ModelProto，得到 250,000 个 piece 及其顺序
3. **逐 id 比对**：以原版 `tokenizer.json` 的词表顺序为基准，与转换后的 spm 逐位置比较

### 3.3 关键数据

```
原版 tokenizer.json（HuggingFace，250,002 条）
  id 0='<s>'  1='<pad>'  2='</s>'  3='<unk>'  4=','  5='.'  6='▁'  7='s'  8='▁de' …
  added_tokens: 0=<s>, 1=<pad>, 2=</s>, 3=<unk>, 250001=<mask>
  model.type = Unigram

转换后 sentencepiece.bpe.model（250,000 条）
  id 0='<unk>'  1='<s>'  2='</s>'  3=','  4='.'  5='▁'  6='s'  7='▁de'  8='-'
  类型：<unk>=UNKNOWN(2)，<s>=CONTROL(3)，</s>=CONTROL(3)；无 <pad>

逐 id 比对 250,000 个位置：
  完全同位置一致         : 1
  该 piece 在原版 id+1   : 249,996     ← 99.998%
  该 piece 在原版 id-1   : 1
  无法对应               : 2（即被丢弃的 <pad>、<mask>）
```

### 3.4 对照实验（消融）

固定同一批句子对、同一个模型，只切换两个变量：**正常 id / 错位 id**，**正确特殊词元 / 错误特殊词元**。

| 条件 | 相关均值 | 无关均值 | 区分度 |
|---|---|---|---|
| ① 正常 id + 正确特殊词元 | 0.9083 | 0.6514 | **+0.2569** |
| ② 正常 id + 错误特殊词元 | 0.9088 | 0.6534 | **+0.2554** |
| ③ 错位 −1 + 正确特殊词元 | 0.7185 | 0.8503 | **−0.1318** |
| ④ 错位 −1 + 错误特殊词元（**修复前现状**） | 0.7216 | 0.8553 | **−0.1337** |

**结论**：

- 破坏语义的是 **id 整体错位**（①→③ 区分度从 +0.26 翻转为 −0.13）
- 特殊词元选择错误（①→②）影响仅 0.0015，属于次要缺陷

> ⚠️ 上表是排查阶段的**近似分词**结果（贪婪最长匹配，非真实 SentencePiece 切分），
> 数值偏夸张，仅用于**分离两个嫌疑**。修复完成后用真实分词重测，数据见第 7 节：
> 修复前 −0.0149、修复后 +0.2894。**以第 7 节为准。**

## 4. 根因

### 4.1 机制

两个系统对"特殊词元占几个位置"的约定不同，而 **id 是"位置"而非"名字"**：

```
HuggingFace 约定：  [<s>] [<pad>] [</s>] [<unk>] [正常词...]    ← 特殊词元占 4 个位置
SentencePiece 约定：[<unk>] [<s>] [</s>]          [正常词...]    ← 特殊词元占 3 个位置
```

### 4.2 真正的机制：XLM-R 的 spm 与模型词表差 1 位（`fairseq_offset`）

> **本节在 2026-11-19 晚做过两次更正**：最初的结论是"第三方格式转换工具重排了特殊词元"，
> 随后又改口为"上游仓库自相矛盾"，**两者都被推翻**。以下是被权威源码证实的版本。

模型已确认是 **`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`**，三重证据：

| 证据 | 结果 |
|---|---|
| `tokenizer.json` SHA256 | 与上游仓库**完全一致**（`2c3387be76557bd4…`） |
| `config.json` 的 `vocab_size` | **250037**，与 ONNX 的 `word_embeddings` 行数 `(250037, 384)` 精确吻合 |
| `config.json` 其余字段 | hidden 384 / 12 层 / `max_position_embeddings` 512 / `type_vocab_size` 2，全部对上 |

**关键事实**：本项目所用的 `sentencepiece.bpe.model`（SHA256 `CFC8146A…`），与 **`xlm-roberta-base` 官方发布的 spm 字节完全相同**。

所以这既不是本地转换产物，也不是某个仓库的疏漏——而是 **XLM-R 的既有设计**：
**spm 的原始 id 与 fairseq 词表（即模型实际使用的 token id）相差 1 位。**

| id | fairseq 词表（= 模型 token id） | spm 原始 id（= SentencePiece 库直接返回的 id） |
|---|---|---|
| 0 | `<s>` | `<unk>` |
| 1 | `<pad>` | `<s>` |
| 2 | `</s>` | `</s>` |
| 3 | `<unk>` | `,` |
| 4 | `,` | `.` |
| 之后 | … | …（**每个都差 1**） |

HuggingFace 在 `transformers/models/xlm_roberta/tokenization_xlm_roberta.py` 里**显式补偿**了这一点：

```python
self.fairseq_tokens_to_ids = {"<s>": 0, "<pad>": 1, "</s>": 2, "<unk>": 3}
# The first "real" token "," has position 4 in the original fairseq vocab
# and position 3 in the spm vocab
self.fairseq_offset = 1
self.fairseq_tokens_to_ids["<mask>"] = len(self.sp_model) + self.fairseq_offset
...
return spm_id + self.fairseq_offset if spm_id else self.unk_token_id
```

（`<mask>` 的位置 `250000 + 1 = 250001`，与 `tokenizer.json` 里的值完全吻合。）

**本项目的错误在于：直接用 SentencePiece C++ 库取 spm 的原始 id，却没有实现这个 `fairseq_offset = 1`。**

- 走 **HuggingFace `AutoTokenizer`** → 框架替调用方加了 offset，一切正常
- 走 **SentencePiece 原生库**（C++ 集成）→ **必须自己加 offset**，本项目漏了 → 整体错位 1 位

> **所以这不是上游的 bug，不需要向上游报 issue。** 该模型 2500 万+ 下载量中绝大多数走 Python + `AutoTokenizer`，
> 永远碰不到；只有绕过 HF、直接用 SentencePiece 原生库的集成（如本项目）会踩中。

> 本项目的修复（重建 spm 使 piece 顺序与模型 id 一致，并写入 `pad_id=1`）**等价于把 `fairseq_offset` 固化进文件**，
> 从而不再依赖调用方记得加偏移。

### 4.3 一个反直觉的比例

> 出错的是 **4 个特殊词元**（占词表 0.002%），被破坏的是 **249,998 个正常词元**（99.998%）。

位置编号会把局部错误放大成全局错误。

### 4.4 用非术语的方式理解

- **模型** = 一整墙储物柜，每个格子有固定编号，格子里放着一件"含义"（384 维向量）。柜子不知道自己做的是谁的柜子。
- **分词器** = 一本索引册，写着"词 A → 3 号柜"。
- 索引册的排版规则换了，全班柜号往前挪一格，于是"词 A → 4 号柜"，打开取到的是词 B 的含义。
- **柜子不会抗议**，因为它本来就没有名字。

## 5. 为什么长期未被发现

这是典型的 **silent failure**（静默失败）。四个条件同时成立：

1. **格式合法** —— protobuf 可解析，`Load()` 返回 ok
2. **每次查询都有返回值** —— `PieceToId()` 对任何输入都返回合法 id，只是对不上
3. **永不越界** —— 词表 250,000 ≤ 模型 250,037 行，模型照查不误
4. **症状伪装** —— 不崩溃、不出 NaN，只表现为"效果不太好"，极易被归因为模型选小了 / 阈值没调好 / 模板写得不好

**根本原因：整条链路上没有任何一个步骤会因为"语义错误"而失败，也没有任何回归测试。**

## 6. 修复方案

### 6.1 方案一：代码内做 id 重映射（备选，**最终未采用**）

把转换后的 id 映射回模型期望的 id：

```
转换后 id → 模型期望 id
0 (<unk>) → 3
1 (<s>)   → 0
2 (</s>)  → 2
n ≥ 3     → n + 1
```

同时把 `bos / pad / eos` 改为 `0 / 1 / 2`，并把 **attention mask 改为按真实长度生成**（不再依赖 pad id，见 6.3）。

- 优点：纯算术，无需新文件，可立即用对照实验验证
- 缺点：属于"补丁"，可读性一般

### 6.2 方案二：重建一份无损的 spm ✅ **已采用**

从原版 `tokenizer.json` 重新构建 SentencePiece ModelProto，**保持 piece 的原始顺序**，并在 `trainer_spec` 中显式声明：

```
unk_id = 3
bos_id = 0
pad_id = 1
eos_id = 2
```

同时保留 normalizer 的 precompiled charsmap 与各 piece 的 score（score 从原 spm 按 piece 字符串取，从而**保证切分行为不变**）。

- 优点：C++ 侧代码无需改动，`PieceToId("<pad>")` 自然返回正确值；可复现（脚本入 `tools/`）
- 缺点：需要能加载 `.model` 的环境做验证（本项目用自建 C++ 探针，见第 7 节）

**实施产物**

| 文件 | 作用 |
|---|---|
| `tools/rebuild_sentencepiece_model.py` | 生成器。仅用标准库手写 protobuf 读写，无需安装 `sentencepiece`/`protobuf` |
| `tools/spm_probe.cpp` + `tools/CMakeLists.txt` | 验证探针。用项目实际链接的 `sentencepiece.lib` 加载 `.model`，输出特殊词元 id 与逐句分词结果 |

生成器实测参数（从原文件解析得到，非假定）：`trainer_spec` 中 `field 40/41/42/43` 分别是 `unk_id/bos_id/eos_id/pad_id`，
原文件中 `pad_id = -1`（即"无 pad"），这正是缺陷根源；重建时写入 `3 / 0 / 2 / 1`。

### 6.3 顺带修正的次生缺陷 ✅ 由 6.2 自动解决

修复前 `text_preproc.cpp` 用 `PieceToId("<pad>")` 取填充 id。原词表无 `<pad>`，该调用回退为 `unk_id`（0），于是：

- 填充位置实际写入 `<unk>`（0）
- `mask[i] = (ids[i] != pad)` 等价于 `ids[i] != 0`，对普通文本恰好等价于长度掩码，属于歪打正着
- 但**正文中真实的 `<unk>` 也会被一并 mask 掉**

重建后 `<pad>` 存在且 `pad_id = 1`，`PieceToId("<pad>")` 返回 1，`<unk>`（id 3）不再被误 mask，**该次生缺陷随主缺陷一并消失，C++ 代码无需改动**。

> 仍建议后续把 mask 改为"按真实长度生成"以彻底解耦（mask 是长度信息，不是词汇信息）：
>
> ```cpp
> const size_t real_len = std::min(ids.size(), (size_t)max_len_);
> ids.resize(max_len_, 0);
> mask.assign(max_len_, 0);
> std::fill(mask.begin(), mask.begin() + real_len, 1);
> ```
>
> 这不是修复本缺陷的必要条件，属于加固。

### 6.4 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 重排模型的 embedding 行以适配错误分词器 | 功能上等价（重排 = 重新编号），但要改写 448MB 权重，风险与收益完全不成比例 |
| 引入 HuggingFace tokenizers 的 C++ 库直接读 `tokenizer.json` | 可彻底避免转换，但为一个小项目引入额外重依赖不划算 |

## 7. 验证方法与实测结果

**修复是否成功，不看它能不能跑，看区分度是否转正。**

验证分两级，缺一不可：

### 7.1 一级：切分行为不变（用真实 `sentencepiece.lib`）

用 `tools/spm_probe.cpp` 分别加载新旧两份 `.model`，对同一批句子分词，比较 **piece 字符串序列**：

| 检查项 | 结果 |
|---|---|
| 9 句的 piece 字符串序列是否逐字一致 | ✅ 完全一致 |
| id 是否恰好按预期 +1（老 id≥3 → 新 id+1） | ✅ 违规 0 条 |
| 特殊词元 | 旧：`<s>=1 </s>=2 <unk>=0`，`<pad>` 回退为 0<br>新：`<s>=0 <pad>=1 </s>=2 <unk>=3 <mask>=250001` |

一级通过，说明**只是编号变了，切法没变**——这正是"无损重建"的定义。

### 7.2 二级：语义区分度（用真实分词 id 跑模型）

固定模型、固定 9 句语料（3 组相关 + 3 组无关），只切换分词表；序列构造完全复刻 `text_preproc.cpp`。

| | 相关对均值 | 无关对均值 | **区分度** |
|---|---|---|---|
| 修复前（错位 spm） | 0.6860 | 0.7010 | **−0.0149** |
| 修复后（重建 spm） | 0.8852 | 0.5957 | **+0.2894** |

逐对明细（修复后）：相关 0.827 / 0.910 / 0.918，无关 0.614 / 0.511 / 0.662 —— 三组全部正确分离。

**结论：区分度由 −0.0149 转为 +0.2894，修复有效。**

### 7.3 端到端

将重建后的 `.model` 放入运行目录，程序启动日志：

```
[INFO] SentencePiece加载成功
[INFO] ONNX模型加载成功
```

悬浮球正常显示，工作集约 561MB（模型确已载入），无错误弹窗。

> 注：验证时必须**固定模型、固定句子、只改分词表**，否则无法归因。

## 8. 预防措施

### 8.1 黄金样例回归测试（最高性价比）

准备 10~20 组人工标注的句对，任何涉及**分词 / 词表 / 模型替换**的改动后跑一遍，断言区分度为正。

成本约半小时，可在本缺陷出现当天就抓到它。

### 8.2 启动期断言

- 校验 `processor_.GetPieceSize()` 与模型 `word_embeddings` 行数是否匹配
- 校验 `PieceToId("<s>")`、`PieceToId("</s>")` 对应 piece 的**类型是 CONTROL 而非 UNKNOWN**（后者说明发生了静默回退）

### 8.3 可迁移的判断原则

> 凡是"按位置编号"的数据——词表、embedding 行、数组索引、数据库自增 id、表格行号——**「转换」这个动作都必须先回答：它保留的是字节，还是语义？**

对这类数据，**格式能互转 ≠ 编号等价**。

> 当两个组件之间传的是"编号"，就必须验证编号对齐；验证方式不是读文档，而是**构造一个能失败的实验**。

---

## 9. 复现步骤

1. 取原版 `tokenizer.json`（`model.type = Unigram`，250,002 条，特殊词元 `<s>=0/<pad>=1/</s>=2/<unk>=3`）
2. 用 SentencePiece 默认约定重建为 `.model`（meta 词元重排为 `<unk>/<s>/</s>`，丢弃 `<pad>`）→ 词表变为 250,000 条且整体前移 1
3. 用该 spm 分词得到 id，送入模型取 CLS 向量
4. 对若干组"相关/无关"句对计算余弦 → 观测到区分度为负
