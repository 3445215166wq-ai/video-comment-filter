# 案例：相似度恒定 84.53%

> 这是本项目**最早**的一个静默 bug（2026-03-28），也是我第一次独立完成
> 「造判据 → 排除假设 → 缩范围 → 定位」的完整排查。
>
> 当时我只查到「分词有问题」就停了，**没有弄清为什么是"恒定"而不是"随机"**。
> 2026-11-21 补做了复现实验，机制才算闭环。实验脚本：`tools/repro_byte_tokenizer.py`（可重跑）。

---

## 一、现象

程序不崩、不报错、日志照打、滚动正常。但：

- 第一次运行后，**相似度就再也不变了**
- 日志里五组长度完全不同的抓取文本——**1522 / 1118 / 1005 / 896 / 497** 字符——
  算出来的相似度**全是 84.53%**
- 补一条对照：`input_ids` 前 10 个明明不同，相似度仍然是 84.53%

## 二、当时的排查路径

| 步骤 | 动作 | 结论 |
|---|---|---|
| 1 | 从日志里把五组不同长度的输入并排拉出来对比 | 相似度不随输入变化 → 排除抓取/清洗/滚动，锁定编码层 |
| 2 | 打印 `input_ids` 前 10 个，确认输入在变 | 输入在变、输出不变 → 排除「文本没更新」这一支 |
| 3 | 检查 `tokenize` 实现 | 发现是 `token_id = 256 + 字节值`，注释还写着「和原模型完全一致」 |
| 4 | 换成 SentencePiece 0.2.1 | 相似度第一次发生变化（40.80%），确认分词是主因 |

## 三、真正的机制（2026-11-21 复现确认）

**两层缺陷叠加，缺一不可。**

### 第一层：页头占满了 `max_len=64` 的窗口

每次从抖音页面复制的文本，开头都是同一段 **246 字节**的页头：

```
开启读屏标签读屏标签已关闭
下载抖音精选
2026 © 抖音
京ICP备16016397号-3
icon京公网安备 11000002002046号
广播电视节目制作经营许可证
京B2-20170846
网络文化许可证-京网文-（2025）0181-061号
```

而当时的 `max_len = 64`，只留 62 个槽位给正文。**页头把窗口全部吃掉，真正的评论一个字都没进模型。**

实测：

```
三段完全不同视频的抓取文本（健身 / 耳机 / 吵架）：
  前 64 个 token 逐位相同   →  64 / 64
  模型输出向量逐元素相同     →  True
  余弦相似度                →  100.0000% / 100.0000% / 100.0000%
```

输入完全相同，输出自然完全相同。所以与模板的余弦是**恒定的**——那个 84.53%
就是「模板向量 vs 页头向量」的固定值，与评论内容毫无关系。

### 第二层：即使清洗掉页头，分词仍然是错的

字节级分词把所有中文压进词表 `304–495` 这一小段——**占 250,037 词表的 0.077%**。
实测 4 条完全不同的评论只用到 72 个不同 token：

实测（同一批文本，仅清掉页头、分词仍然错）：

```
健身 vs 耳机（不同话题）  87.23%
健身 vs 吵架（不同话题）  91.89%   ← 比"相关"的还高
```

更完整的一组（以 3 条健身评论的均值为模板，测 7 条评论）：

```
健身相关   82.68%   91.10%
耳机无关   79.25%   80.96%   83.79%
吵架内容   86.25%
完全无关   90.44%   ← 天气话题，比健身还高
均值       84.92%（与当年日志里的 84.53% 几乎重合）
```

全部挤在 **79–91%** 之间，且**排序毫无意义**。这正是后来反复出现的
「洗得越干净，相似度反而越高」「买耳机的比健身还高」的根源。

## 四、修复

| 层 | 修复 | 结果 |
|---|---|---|
| 第一层 | 清洗阶段删掉页头（按行/关键词规则），并让 `max_len` 扩到 128 | 评论内容真正进入模型 |
| 第二层 | 改用 SentencePiece 0.2.1 做子词分词 | 相似度首次出现有意义的差异（40.80%） |

## 五、教训

1. **「输入在变、输出不变」是最强的定位信号**——它一次性排除了整条上游链路，
   比逐个模块排查快得多。这个判据是自己从日志里挖出来的，不是谁教的。
2. **注释写着"和原模型完全一致"的地方，最值得怀疑**。那句话本身就是错误的来源。
3. **`skip_tokens` 那行注释说明我当时已经摸到边了**：
   `// 调试时不要跳过token；上线可调回200以跳过固定前缀` ——
   "固定前缀"就是页头，只是当时没把它和"相似度恒定"连起来。
4. **长度固定的输入窗口 + 长度不固定的页头，是一个必然会踩的坑**：
   抓取类程序要永远假设"开头有一大段我不关心的东西"。
5. 修完第一层之后症状变了但没消失（清洗完仍然没区分度），**说明还有第二层**——
   症状变化不等于问题解决，要重新造判据。

## 六、这条案例在面试里怎么讲（约 40 秒）

> 程序不报错，但相似度永远是 84.53%。我把日志里五组长度完全不同的输入拉出来对比——
> 1522、1118、1005、896、497 个字符，相似度一个不差。这一下就排除了抓取、清洗、滚动，
> 把问题锁在编码层。
>
> 后来复现才发现是两个缺陷叠加：一是每次抓的网页文本开头都有 246 字节的页头，
> 而我的输入窗口只有 64 个 token，页头把窗口占满，真正的评论根本没进模型——
> 所以输入完全相同、输出完全相同。二是分词我写成了「字节值加 256」，
> 等于没做子词分词，所有中文都压进词表的一小段，向量彼此高度相似，排序没有意义。
>
> 改成 SentencePiece 之后，相似度第一次出现了有意义的差异。
