# 经验教训（Lessons Learned）

> 这份文档只装**可迁移的教训**——换一个项目仍然成立的那些。
>
> 分工别混：
> - `ENGINEERING_LOG.md` —— 时间线，"哪天做了什么"
> - `TOKENIZER_ALIGNMENT.md` —— 单次事故的完整复盘
> - **本文件** —— 从事故里提炼出的、能防下次的规则与自检清单
>
> 每条教训的格式固定为：**现象 → 我当时的判断 → 实际是什么 → 自检问题**。
> 最后一项是关键：教训要能被"用一句话问出来"，否则记了也不会用上。
>
> 本文不做美化处理：作者本人的判断错误、被推翻的结论、被纠正的过程，都如实保留。

## 一、这次是怎么被发现的（转折点记录）

这个项目里最严重的问题（分词表 id 偏移、语义筛选全程失效）**不是靠看报错发现的**——它不报错。
它是被一串**来自项目作者本人的质疑**逐步逼出来的。记录这些转折点，因为它们比结论本身更有方法论价值。

### 转折点 1｜"我看网络没什么问题啊"

| | |
|---|---|
| 我当时的判断 | "国内访问 GitHub 必须挂代理"——依据只是 `github.com` 首页直连要 20 秒 |
| 质疑 | **「为啥会这么慢？我看网络没什么问题啊」** |
| 结果 | 分通道测速后发现：代理 76 KB/s，**直连 1505 KB/s，快 20 倍**。前提整个是错的 |
| 打法 | **当事人对自己环境的直觉，优先于我从零散现象推的结论** |

### 转折点 2｜"我放的不是 MiniLM 的模型吗"

| | |
|---|---|
| 我当时的判断 | "这不是 MiniLM"——依据只是 `model.onnx` 有 448 MB |
| 质疑 | **「话说我放的不是 MiniLM 的模型吗？只是用 python 转了一下，然后分词表用另外一个体系而已啊」** |
| 结果 | 实测 117.5M 参数 / 384 维 / 12 层 → 确实是**多语言** MiniLM。448 MB 来自 250k 词表的嵌入矩阵 |
| 打法 | **一手记忆 vs 二手推断**——他记得自己下载的是什么；我只是在猜 |

### 转折点 3｜"我按照操作来的呀怎么会错呢"

| | |
|---|---|
| 关键线索 | **「我好像是因为那个版本的不能在 C++ 里用，所以需要转换啥的，我按照操作来的呀怎么会错呢」** |
| 意义 | 这句话给出了真实的操作路径（**下载 + 转换**），而不是"随手改坏了"。方向从此从"找谁弄坏的"转向"转换这一步到底做了什么" |

### 转折点 4｜"那个仓库能自相矛盾吗"

| | |
|---|---|
| 我当时的判断 | "上游仓库自带的两套分词表互相矛盾" |
| 质疑 | **「那个仓库能自相矛盾吗？github 上自相矛盾的是不是很多？」** |
| 结果 | 这个质疑逼我去下载 `xlm-roberta-base` 官方的 spm 做字节比对 → **完全相同**。于是"上游矛盾"也被推翻，最终去读 transformers 源码，才找到 `fairseq_offset = 1` |
| 打法 | **用常识检验叙事**——2500 万下载量的模型不太可能犯这种矛盾，一定是我漏了机制。**这个质疑直接把我从第二次错误结论里拽出来** |

### 转折点 5｜"提 issue 算简历吗？采纳率多少？有人维护吗？"

| | |
|---|---|
| 我起初的倾向 | "你发现了一个上游 bug，可以报 issue" |
| 质疑 | **「提 issue 甚至解决方案算不算可以写进简历的事情？被对方采纳的成功率是多少有人维护这个库吗？」** |
| 结果 | 查证后发现：这不是 bug，是文档化的设计；transformers 仓库六年无人报过同类问题。**结论改成"不该报 issue"**，避免了一个错误行动 |
| 打法 | **先评估可行性与被接纳概率，再决定做不做**——而不是"看起来能加分"就上 |

### 转折点 6｜"我怎么没有 XLMRobertaTokenizer 这一层"

| | |
|---|---|
| 我起初的解释 | 反复讲"层""包装"，但没讲清那一层到底干什么 |
| 质疑 | **「我的意思是我怎么没有 XLMRobertaTokenizer 这一层，这是干嘛的？」** |
| 结果 | 对比之后发现：**`text_preproc.cpp` 里那段代码就是手写的 `XLMRobertaTokenizer`**——特殊词元、切词、填充/mask 都做了，四件事里只漏了 offset 这一件 |
| 打法 | **追问概念本身，而不是接受模糊说法**。这一问把"我缺了个东西"变成了"我少了一条规则" |

### 转折点 7｜"其实应该写进代码里的，这样最能解耦"

| | |
|---|---|
| 我当时的建议 | 重建分词表、把偏移固化进文件，理由是"C++ 代码零改动" |
| 质疑 | **「那被你骗了啊，其实应该写进代码里的，这样最能解耦，你这样的话就相当于自己拆了一个独立零件」** |
| 结果 | 改判为代码侧补偿，分词表恢复上游原版 |
| 打法 | **从架构原则否掉能跑通的方案**。前 6 次质疑的是"事实对不对"，这一次质疑的是"**评价标准对不对**" |

### 这七次质疑的共同点

不是"钻牛角尖"。钻牛角尖是在无关细节上纠缠；这七次每一次都正好打在**当时错误的那一环**上，而且种类不同：

| 类型 | 作用 | 例子 |
|---|---|---|
| 一手经验对照 | 推翻二手推断 | 转折点 2、3 |
| 常识性质疑 | 推翻不合常理的叙事 | 转折点 4 |
| 追问意义与可行性 | 避免无用功 | 转折点 5 |
| 追问概念本身 | 把模糊认识钉死 | 转折点 6 |
| 用原则压方案 | 改变最终设计 | 转折点 7 |

> **给我的启示**：我手里有全部信息，却连续两次用"构造叙事"代替查证，在错误的坐标系里越算越自洽。
> 打破这个循环的，是**系统外部的、与我假设冲突的信号**。
> 所以流程上必须假设"没有人会在旁边喊停"，把质疑内建成自检清单（见第三节）。

## 二、可迁移的教训

### L1 先测相关量，别用邻近指标

- **现象**：连续三次拿"手边容易测的东西"代替"真正相关的那个量"
- **当时的判断**：① 首页延迟 20 秒 → 上传也会慢；② 文件 448 MB → 不是 MiniLM；③ 某进程挂 40+ 连接 → 它在偷流量
- **实际是**：① 上传端点直连快 20 倍；② 是多语言 MiniLM，体积来自词表；③ 该进程实测 IO 为 0
- **自检问题**：**我测的这个量，和我要回答的问题，是同一个东西吗？**

### L2 归因"是谁弄坏的"之前，先取一手来源做比对

- **现象**：看到分词表 id 与预期不符，直接判定"被第三方转换工具搞坏了"
- **实际是**：那份文件是上游原厂文件，一字节没动
- **自检问题**：**我能拿到原始来源做哈希比对吗？拿到了再下结论。**

### L3 追溯根因要读权威源码/规范，别从现象构造叙事

- **现象**：同一个根因我**改判了三次**（第三方工具 → 上游矛盾 → `fairseq_offset`），前两次都是从现象编故事
- **自检问题**：**这个结论出自哪个一手来源？说不出出处就先标"待验证"，不要写成结论。**

### L4 方案评审要同时看实现成本与耦合度

- **现象**：我把"C++ 代码零改动"当成了优点，还用"属于补丁、可读性一般"贬低了更优方案
- **实际是**：改输入产物 = fork 上游 = 耦合升高；改边界代码才是解耦，而且更显式
- **自检问题**：**如果我在用"省事/能跑通/数值对得上"当理由，那么这两个方案在耦合度上谁更好？**

### L5 不要 fork 上游产物，适配放在边界

- **现象**：为了省掉几行代码，重建了一份"只有本项目理解"的分词表
- **实际代价**：别人拿它配标准工具会重复适配（偏移两次）；上游更新时会漂移
- **自检问题**：**我这份产物，别人拿去按标准方式用会怎样？**

### L6 验证要用真实组件，近似品只能用来排除嫌疑

- **现象**：我用贪婪最长匹配近似分词，算出区分度 −0.1337 并宣称"语义系统性反转"
- **实际是**：换成真实 `sentencepiece.lib` 后只有 −0.0149，正确表述是"区分度失效"
- **自检问题**：**这个数字是真实组件跑出来的，还是我用近似品算的？如果是后者，有没有标注口径？**

### L7 生成物必须可重建，且不得比源码陈旧

- **现象**：一个展示着已修复 bug 的 Doxygen 文档，占了 250 MB / 18,016 个文件
- **自检问题**：**这份东西能从源码一条命令重新生成吗？它现在和代码一致吗？**

### L8 "看起来正常"是一个待验证项

- **现象**：本项目的两个最严重缺陷（中文路径加载失败、id 偏移）都不报错
- **自检问题**：**除了"它没崩"，我还有什么证据说明它是对的？**

### L9 产物可删，过程必须留

- **现象**：曾把"建议删掉"讲成"没价值"
- **正确区分**：**可再生的派生物**（构建产物、生成的文档）本体可删，只需记录"怎么生成"；**不可再生的知识**（决策理由、踩坑过程）必须用文字留
- **自检问题**：**这个删掉之后，还能重新得到吗？得不到的部分我记下来了吗？**

## 三、给自己（以及未来的协作者）的检查清单

在**下结论**之前：

- [ ] 这个结论出自哪个一手来源？出处能说出来吗？
- [ ] 我测的量，和要回答的问题，是同一个东西吗？
- [ ] 有没有一条与我假设冲突的证据被我"解释掉"了？

在**换方案**之前：

- [ ] 两个方案的耦合度谁更好？（而不是谁的改动量更小）
- [ ] 我有没有用贬义词给某个方案贴标签，从而让它看起来更差？
- [ ] 我改造的是产物，还是边界？

在**删东西**之前：

- [ ] 它会失去什么？用什么更小的代价替代？
- [ ] 这是可再生的派生物，还是不可再生的知识？

在**验证**之前：

- [ ] 我跑的是真实组件，还是近似品？
- [ ] 这个实验**有可能失败**吗？如果它怎么跑都会通过，那它没有验证任何东西
